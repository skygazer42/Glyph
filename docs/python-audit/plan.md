# Python 全文件审核与整改计划

日期：2026-11-15。基线：`034a661`。依据：`python-coding-guidelines`。

## 范围与验收

- 审核仓库拥有的每一个 Python 文件，包括入口、包导出、示例、脚本、种子数据脚本与测试；第三方依赖、虚拟环境、缓存及 `temp/` 运行副本不重复审核。
- 逐文件记录已读范围、发现的问题、规则编号、实际改法、保留理由及验证结果。无问题的文件也必须留记录。
- 保留现有业务功能、公开接口、导入契约及配置语义；不新增依赖，不自动提交、迁移数据库或部署。
- 不把推荐项升级成强制项，不机械删除所有默认值、异常处理、工厂或小模块。

## 整改顺序

1. 建立完整文件清单，记录 Git 状态、语法、pytest、Ruff 与类型检查基线。
2. 在修改具体行为前先增加或运行必要的离线回归测试；区分现有故障与本次回归。
3. 优先修复语法和未定义名称、必需字段与零值混淆、资源关闭、异常传播、异步阻塞和取消问题。
4. 按实际引用删除无用代码与导入，简化重复与多余分支；公开导出和注册副作用必须保留。
5. 检查 Pydantic v2、FastAPI、数据库事务和 HTTP 客户端契约，保持响应与调用方一致。
6. 每个分区独立验证；主代理复核变更、覆盖清单和跨分区调用，再运行统一检查。

## 并行所有权

按用户最新要求，只运行两个子智能体，分批处理六个分区，共享工作区，互不覆盖他人改动；所有权以 `inventory.json` 为准。

- 子智能体一：`api_config` → `persistence_chatdb` → `runtime`。
- 子智能体二：`tooling` → `packs_dsl` → `knowledge_pipeline`。
- 前一轮被中断和限流的其它子智能体保持停止，不产生额外并发。

| 分区 | 范围 |
| --- | --- |
| api_config | API、配置、核心工具、领域目录、根入口与 app 入口 |
| persistence_chatdb | ORM、schema、持久化与 ChatDB |
| runtime | Agent framework、service、domain、models 与 agents 包入口 |
| packs_dsl | Agent packs 与 DSL 生成器 |
| knowledge_pipeline | 知识模块与 Agent pipeline |
| tooling | 脚本、示例、数据种子和现有测试 |

各分区仅新增自己的回归文件 `tests/test_python_guidelines_<分区>.py` 和审核记录 `reviews/<分区>.json`。跨分区改动先交给主代理协调。

每条文件记录必须包含 `path`、`reviewed_lines`、`full_file: true`、`status`、具体 `summary`、`rules`、`findings`、`validation` 和 `remaining`。问题记录列出规则编号、级别、行号、问题、影响、修改或保留理由。职责评审包含 DES-003 的合并判断，不为减少文件数强行合并。

主代理维护基线工具版本、命令、退出码，修正现有测试忽略规则，使新增回归测试可被版本管理识别；最终重新扫描所有项目 Python 文件，补审新增文件，并交叉复核回归测试。

## persistence_chatdb 具体整改顺序

先用离线回归锁定空密码、连接/游标关闭、失败传播、schema刷新外键与缓冲并发行为；再删除DBAccess重复包装，保留全部八种方言和公开调用入口，统一它实际拥有的连接关闭。元数据刷新按既有整体提交边界补齐依赖删除/失败回滚，保留ORM注册与公开schema文件。流缓冲在await前取走本批数据，明确空字典结果与错误消息；不移动借用的ORM Session到工作线程。最后修正Pydantic v2序列化和实际SDK契约，运行离线回归、Ruff、编译和跨模块mypy。

## 主代理集成复核整改

- 内置三类 DSL 模板先补公开生成到执行的回归，再以现有表达式语法替换不可执行的多行 Python 和未定义平铺变量；保留原参数、档位顺序与补贴公式，不扩大解释器能力。
- 主代理全文复核监控与安全网关后接管这两个文件。先覆盖零值、监控失败后的间隔、阻塞采样/邮件的线程归属、日志资源与认证配置；再修清理、错误传播和导入副作用，保留现有权限与限流业务。
- 两个子智能体继续其余运行时和知识模块，主代理新增的回归文件同样纳入最终全文件审核清单。
