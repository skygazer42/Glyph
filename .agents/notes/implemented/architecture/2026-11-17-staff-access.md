# Agent Note: 工作人员认证与公众隔离

Status: implemented

## Problem

用户指出后台和公众咨询可以直接互相进入。已有 /agent 与 /workbench 只区分页面，api_server.py 管理路由没有认证，后端智能路由还会替公众选择默认业务数据库。单加登录页面无法保护实际接口和资料。

## Decision

沿用当前配置账号与 python-jose，增加 /api/auth/login、session、logout。认证JWT只进HttpOnly、SameSite Strict、/api作用域Cookie；工作人员写请求验证CSRF。主API的知识库、图谱、规则、数据库路由统一要求工作人员身份，不依赖旧入口disable_auth。前端路由在挂载后台前拦截，登录后回到安全的原模块地址。新账号体系、注册与密码找回均不加入。

共享咨询由服务端确认入口权限。工作人员会话以用户名摘要分区；公众会话使用随机存储ID和有期限的签名凭证，凭证只能通过POST请求体与SSE返回，避免放进URL访问日志。会话列表、读取历史与删除API只对工作人员开放；公众仍阅读浏览器本地记录，不提供携带凭证的GET URL。私有参数和附件路径在服务依赖初始化前校验。AgentService请求上下文携带可信私有工具权限，公众不能默认连接数据库、执行Text2SQL或检索用户档案。

公众缓存保留原localStorage；工作人员缓存按账号放sessionStorage，退出清理自己的标签页缓存和Pinia资料/规则状态。服务器会话ID与本机记录ID分开，首次服务端返回不会丢掉本机历史或复制会话的服务器归属。切换身份时旧响应和重试不能写回新账号状态。

附件新增public与staff/账号摘要目录；工作人员上传与下载均认证。公众上传是不可列举的随机URL，只能用于公开咨询材料。已有平铺附件保留在磁盘但不通过公众路由继续公开，避免把无法判断归属的旧文件归给公众。

## Alternatives considered

- 只守前端路由：直接请求接口仍可读写，不能满足登录边界。
- 把JWT放localStorage或URL：扩大脚本与日志泄露范围，因此认证仅用Cookie，公众凭证放POST体。
- 新建账号表和完整RBAC：当前仅需分开公众与配置工作人员，新增迁移和管理流程超出本次需求。
- 自动迁移旧会话/旧附件：历史数据没有工作人员所有者，自动分配会误归属，保留原件并隔离。

## Consequences

部署需配置工作人员账号、密码、至少32字节签名密钥；未配置返回503，不伪造成功。当前仅支持配置工作人员账号，退出删除当前浏览器Cookie；已复制Cookie在到期或轮换签名密钥前仍有效。没有服务端撤销表、多账号管理或单独发布知识库语料的权限模型。

按用户“暂时不测试”的要求，新增回归与调用方更新均未执行；未运行测试、lint、构建、服务或数据库。只查看真实登录页1440×900与390×844浅色/深色排版，真实登录和后台权限联调仍需配置后验证。证据位于 .oil-ui/staff-access-r18/shots/。
